Базовая функциональность, необходимая для корректной работы приложения и выполнения его основной цели: массовый импорт Markdown-файлов в GitHub Issues и экспорт существующих Issues обратно в Markdown, в рамках одного выбранного репозитория, через экраны Upload и Download.

## 1. Платформа и общий интерфейс

* В главном окне доступны два основных экрана: Upload и Download.
* Настройки доступны отдельно; горячая клавиша открытия настроек — `Ctrl+,`.
* Переключение репозитория во время активной операции запрещено: соответствующая кнопка недоступна, а попытка такого изменения должна быть невозможна также на уровне проверок состояния.

## 2. Авторизация GitHub

* Для работы с GitHub используется токен пользователя.
* Токен вводится через графический диалог.
* После ввода токен сразу проверяется.
* Сохранённый токен никогда не отображается полностью.
* Токен хранится между запусками приложения.
* Хранение выполняется через Windows Credential Manager / DPAPI.
* В настройках должна быть возможность удалить сохранённый токен.
* Перед удалением токена требуется подтверждение.
* При истёкшем, отозванном или недостаточном для операции токене приложение сообщает понятную причину и предлагает заменить токен.
* В верхней части интерфейса отображаются иконка и название авторизованного GitHub-аккаунта.
* GitHub API используется только через сеть; остальные данные и состояние приложения хранятся локально.
* Для получения списка доступных репозиториев должны учитываться репозитории владельца, репозитории, где пользователь является collaborator, и репозитории, доступные через членство в организациях. Это соответствует механизмам GitHub API для `owner`, `collaborator` и `organization_member`.

## 3. Выбор репозитория

* В верхней части главного интерфейса постоянно отображается текущий репозиторий.
* Компонент выбора показывает название репозитория и кнопку смены.
* Нажатие кнопки открывает встроенный диалог выбора репозитория.
* Диалог содержит поле для вставки GitHub URL и кнопку отправки рядом с ним.
* Ниже находится выпадающий список репозиториев текущего аккаунта.
* Список репозиториев загружается заново при каждом открытии диалога.
* В течение одного открытия диалога полученные данные кэшируются.
* В диалоге есть отдельная кнопка принудительного обновления списка.
* Список поддерживает поиск.
* Для каждого репозитория отображаются название, приватность и обладатель/организация.
* В список попадают только репозитории, к которым авторизованный пользователь имеет доступ, включая приватные репозитории, репозитории организаций и репозитории, где пользователь является collaborator.
* URL репозитория должен обрабатываться максимально терпимо к допустимым вариантам GitHub URL, включая завершающий `/`, `.git`, `/issues` и ссылки на конкретные Issues.
* При разборе URL нельзя допускать неконтролируемой интерпретации точек, слешей и других элементов URL как частей локальных путей или имён файлов. Необходимо реализовать надёжную защиту от инъекций.
* Некорректный или недоступный репозиторий приводит к понятной ошибке.
* При смене репозитория текущая временная Upload-очередь не очищается.
* Репозиторий нельзя менять во время активной операции.

## 4. Экран Download

* Экран Download предназначен для просмотра существующих Issues выбранного репозитория и скачивания их в Markdown.
* Issues отображаются карточками.
* На одной странице отображается 10 карточек.
* Список автоматически загружается при открытии экрана и при смене репозитория.
* Должна быть кнопка принудительного обновления.
* Следующая страница загружается при переходе пользователя на неё.
* Загруженные страницы кэшируются.
* Для получения списка Issues приложение должно использовать серверные возможности GitHub API, а не загружать весь набор и сортировать/фильтровать его локально.
* GitHub API для списка repository issues поддерживает фильтрацию по состоянию и labels, а также сортировку по `created`, `updated` и `comments` с направлением `asc`/`desc`; параметр `per_page` поддерживает до 100 элементов. Поэтому интерфейс не должен обещать сортировку или фильтрацию, которых нет в соответствующем API.
* Должен быть фильтр по статусу `open` / `closed` / при необходимости `all`, если он поддерживается используемым запросом.
* Должен быть поиск по title в пределах возможностей GitHub API; если конкретная операция поиска не поддерживается endpoint'ом списка repository issues, она должна быть реализована через соответствующий GitHub API-механизм, а не через скрытую полную локальную загрузку репозитория.
* Должен быть фильтр по labels.
* Должна быть сортировка по доступным GitHub API полям.
* Сортировка и фильтрация не должны выполняться над всем набором Issues локально.
* На карточке отображаются номер Issue, title, статус и labels.
* Labels отображаются цветными метками; цвет должен соответствовать цвету соответствующего label на GitHub.
* Body Issue на карточке не отображается.
* Для каждого Issue доступна кнопка Download.
* Для каждого Issue доступна кнопка Open in Browser.
* Карточка должна отображать состояние скачивания.
* Пользователь может выделить несколько Issues и выполнить массовое скачивание отдельной кнопкой.
* Массовое скачивание можно отменить.
* Pull requests, возвращаемые GitHub Issues API, должны быть отличимы от обычных Issues и не должны ошибочно экспортироваться как обычные Issue. GitHub прямо указывает, что Issues endpoint может возвращать pull requests.

## 5. Формат Download

* Каждый скачанный Issue сохраняется отдельным Markdown-файлом.
* Заголовок Issue используется как title файла.
* Body Issue становится содержимым Markdown-файла.
* Никакие дополнительные метаданные в текущей версии в Markdown не записываются.
* Если содержимое body не заканчивается переводом строки, перед сохранением добавляется один перевод строки.
* Имя файла имеет формат `номер-title.md`.
* Расширение `.md` добавляется автоматически.
* Недопустимые для Windows символы в title заменяются на универсальный видимый символ-заполнитель; конкретный символ выбирается реализацией.
* При формировании имени должны учитываться зарезервированные Windows имена и ограничения файловой системы.
* Длина итогового имени файла должна ограничиваться с учётом реальных ограничений Windows и GitHub API; реализация не должна допускать создание заведомо некорректного пути.
* При существующем файле приложение не должно автоматически его перезаписывать.
* Если существующий файл и скачиваемый Issue имеют абсолютно одинаковое содержимое, операция может завершиться без пользовательского запроса.
* Если содержимое отличается, пользователь должен явно выбрать дальнейшее действие.
* Возможные конфликты файлов не должны приводить к тихому удалению или перезаписи пользовательских данных.
* Папка назначения выбирается один раз для массового скачивания.
* При отмене массового скачивания уже успешно сохранённые файлы не удаляются автоматически.

## 6. Экран Upload

* Экран Upload предназначен для временной подготовки пачки Markdown-файлов перед созданием GitHub Issues.
* Upload-очередь существует только до подтверждения операции.
* После подтверждения отправки очередь очищается.
* После завершения операции очередь не сохраняется как незавершённая задача.
* Markdown-файлы можно добавлять через drag and drop.
* Markdown-файлы можно добавлять через `Ctrl+V` из Windows Explorer.
* Вставка через `Ctrl+V` должна работать с файлами, папками и путями к файлам.
* Drag and drop и `Ctrl+V` должны приводить к одинаковому результату.
* При добавлении папки Markdown-файлы ищутся рекурсивно.
* Поддерживаются расширения `.md` и `.markdown`.
* Симлинки и junctions принципиально не обходятся.
* Максимальный размер одного Markdown-файла — 1 000 000 символов.
* Бинарные и нечитаемые данные не поддерживаются.
* Для Markdown используется UTF-8 с автоматическим определением допустимых вариантов кодировки.
* BOM должен корректно обрабатываться.
* Исходные Unicode-символы и форматирование Markdown не должны произвольно преобразовываться.
* Если при чтении файла возникает ошибка, добавление останавливается и пользователь получает варианты Retry и Skip.
* Для таких решений доступен вариант Apply to all.
* Если при рекурсивном обходе встречается недоступная папка, добавление останавливается с теми же вариантами Retry, Skip и Apply to all.
* При смешанном добавлении файлов и папок поддерживаемые Markdown-файлы добавляются в очередь, а неподдерживаемые объекты не должны приводить к неконтролируемой ошибке.
* При необходимости интерфейс должен сообщать пользователю о пропущенных неподдерживаемых объектах.
* Если обнаружено более 100 Markdown-файлов, пользователь должен подтвердить продолжение.
* Максимального количества файлов в одной Upload-операции нет.

## 7. Определение title при Upload

* По умолчанию title Issue берётся из имени Markdown-файла.
* Расширение файла удаляется.
* URL-символы в имени файла не декодируются.
* Если имя содержит пробел, символы `-` и `_` не преобразуются.
* Если пробелов нет и присутствует `_`, все `_` заменяются на пробелы, а `-` остаются без изменений.
* Если пробелов и `_` нет, все `-` заменяются на пробелы.
* Title можно вручную изменить непосредственно на Upload-карточке.
* После изменения title именно изменённое значение используется при отправке.
* Исходное имя файла отображается под title серым небольшим текстом и не изменяется.

## 8. Upload-карточка

* Каждый Markdown-файл отображается отдельной карточкой.
* Title отображается крупным редактируемым шрифтом.
* Исходное имя файла отображается ниже мелким серым текстом.
* Body отображается в свёрнутом предпросмотре.
* Labels отображаются как цветные метки.
* Доступны только существующие labels выбранного GitHub-репозитория.
* Новый label непосредственно в Upload UI создать нельзя.
* Цвет каждого label должен соответствовать цвету GitHub.
* Карточка отображает ошибку с красной иконкой предупреждения, если для неё есть ошибка.
* С карточки должны быть доступны операции выбора/изменения labels и другие поддерживаемые в текущей версии метаданные.
* Assignees, связи с другими Issues и другие расширенные метаданные сейчас не должны появляться как неработающие элементы интерфейса.
* Для массового изменения labels и других доступных метаданных пользователь может выделить несколько карточек чекбоксами и применить действие к выбранным карточкам.
* Доступно удаление выбранных карточек.
* `Delete` удаляет выделенные карточки.
* Кнопка удаления запрашивает подтверждение.
* Должна быть кнопка Select All.
* Должна быть возможность снять выделение.
* Должны поддерживаться сортировка и фильтрация Upload-очереди.
* Дубликатом считается элемент, у которого одновременно совпадают title в текущей очереди и хеш содержимого файла.
* Путь к файлу не учитывается при определении дубликата.
* При обнаружении дубликата пользователь получает варианты Replace, Keep both и Skip.
* При выборе Replace существующий элемент очереди заменяется новым.
* При выборе Keep both оба элемента остаются.
* При выборе Skip новый элемент не добавляется.

## 9. Предварительная проверка Upload

* Перед отправкой выполняется локальная предварительная проверка всей очереди.
* Проверка не должна требовать сетевых запросов.
* Проверяются данные, которые можно достоверно проверить локально: наличие title, допустимость подготовленных данных, корректность внутреннего состояния очереди, размер body и отсутствие некорректных значений.
* Проверка не должна выдавать как гарантированный результат то, что может быть установлено только GitHub API.
* Если локальная проверка не пройдена, отправка не начинается до устранения или явного решения пользователя.
* После локальной проверки начинается отправка в GitHub.
* GitHub API создания Issue принимает title и body, а также поддерживает labels и другие дополнительные поля; текущая версия использует только реализованные поля.

## 10. Upload в GitHub

* По умолчанию все создаваемые Issues имеют статус open.
* Каждая Markdown-запись создаёт отдельный GitHub Issue.
* При массовой отправке более 10 Issues перед началом требуется подтверждение пользователя.
* При 10 или менее Issues дополнительное подтверждение перед отправкой не требуется.
* При успешной отправке Issue соответствующая запись считается выполненной.
* При ошибке пользователь получает сообщение вместе с запросом решения.
* Ошибка должна содержать понятное описание причины.
* Пользователь может прервать операцию.
* Пользователь может продолжить операцию.
* При продолжении повторно отправляются только неуспешные Issues.
* Уже успешно созданные Issues повторно не отправляются.
* При прерывании уже успешно созданные Issues остаются в GitHub.
* При частичном успехе приложение не пытается удалить успешно созданные Issues автоматически.
* После завершения подтверждённой операции временная Upload-очередь очищается.
* Перед отправкой выполняется максимально возможная локальная валидация всей пачки, после чего операция выполняется последовательно/пакетно с учётом возможностей GitHub API.
* Полная транзакционная атомарность относительно GitHub API не гарантируется: при сетевом сбое или другой внешней ошибке GitHub может получить только часть пачки.

## 11. Настройки

* Настройки открываются внутри основного окна.
* Доступ к настройкам — через интерфейс приложения и `Ctrl+,`.
* В настройках доступно управление GitHub-токеном.
* В настройках доступно удаление сохранённого токена.
* Другие настройки могут добавляться без изменения основной модели взаимодействия приложения.
* Настройки сохраняются автоматически.

## 12. Клавиатура и быстрые действия

* `Ctrl+V` добавляет поддерживаемые файлы, папки или пути к ним в Upload-очередь.
* `Delete` удаляет выделенные Upload-карточки после подтверждения.
* `Ctrl+,` открывает настройки.
* Все основные действия Upload должны быть доступны без прохождения дополнительных экранов.
* Drag and drop должен обеспечивать тот же пользовательский результат, что и добавление через `Ctrl+V`.
