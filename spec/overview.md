# Upload My Issue — Overview

Upload My Issue — минималистичная Windows-утилита для быстрого массового импорта Markdown-файлов в GitHub Issues и экспорта существующих Issues обратно в Markdown. Пользователь работает только с одним выбранным репозиторием одновременно, выбирает его по GitHub URL или из списка доступных ему репозиториев, а основные операции выполняются непосредственно из двух экранов: Upload и Download. Интерфейс должен минимизировать количество действий, не скрывать потенциально опасные операции и не удалять пользовательские данные без явного подтверждения.

## 1. Платформа и общее оформление

* Приложение работает на Windows.
* Интерфейс и все пользовательские сообщения — на английском языке.
* Всё приложение работает внутри одного окна; дополнительные формы открываются как встроенные диалоги.
* Интерфейс должен оставаться лёгким и минималистичным. Один-два акцентных цвета + красный для "опасных" кнопок.
* Стиль оформления и подсветка выбранных элементов интерфейса (включая рамки карточек и фоновые акценты) должны соответствовать принятому дизайну приложения.
* Во время фоновых операций пользователь может сворачивать окно и переключаться между экранами.
* При закрытии приложения во время операции пользователь получает предупреждение о том, что операция будет прервана; действие продолжения закрытия оформляется как явно опасное, визуально выделенное действие.
* Закрытие приложения во время обычного простоя не требует подтверждения.
* Общий принцип программы: все изменения, требующие от пользователя усилий, не должны теряться без предупреждения.

## 2. Обработка ошибок

* Ошибки авторизации, доступа к репозиторию, rate limit, сети, чтения файлов, валидации и некорректных данных должны различаться.
* Пользователю показывается понятное описание ошибки и доступное действие.
* Для повторяемых сетевых ошибок применяется exponential backoff.
* Для GitHub API rate limit применяется exponential backoff в пределах разумного лимита ожидания.
* После исчерпания попыток пользователь получает ошибку.
* Ошибки отдельных Issues при массовой операции не должны автоматически уничтожать уже успешно выполненные операции.
* Для ошибок чтения файлов и обхода директорий доступны Retry и Skip, а также Apply to all.
* Для ошибок GitHub API пользователь может продолжить или прервать текущую массовую операцию в зависимости от контекста ошибки.
* Текст ошибки можно скопировать в буфер обмена отдельной кнопкой.
* Логи записываются локально в `AppData/upload-my-issue/logs`.
* Логи не должны содержать сохранённый GitHub-токен или другие секреты.
* Логирование не должно само по себе препятствовать основной операции.
* Непредвиденные ошибки (не относящиеся к перечисленным выше категориям) не должны приводить к падению интерфейса в нерабочее состояние или к тихому зависанию: пользователю показывается общее сообщение об ошибке без внутренних деталей, событие логируется, а приложение остаётся в рабочем состоянии либо предлагает перезапуск экрана/приложения.

## 3. Безопасность данных и файлов

* Приложение не должно без явного подтверждения удалять или перезаписывать пользовательские файлы.
* Все операции, потенциально изменяющие пользовательские данные, должны быть безопасными по умолчанию.
* Состояние приложения хранится в `AppData/upload-my-issue/`.
* Сохранение состояния выполняется атомарно.
* Повреждение файла состояния при закрытии или перезапуске во время записи не должно приводить к потере последнего корректного состояния.
* Сохранённый токен хранится отдельно через Windows Credential Manager / DPAPI.
* Локальные файлы состояния не должны содержать токен в открытом виде.
* Рекурсивный обход директорий не должен следовать за symlink/junction.
* URL и пути должны обрабатываться с защитой от path traversal и других форм подмены локального пути.
* Ошибки и логи не должны раскрывать секретные данные.

## 4. Автосохранение состояния

* Настройки и состояние интерфейса сохраняются автоматически.
* Сохранение выполняется после любого изменяющего состояние действия.
* Загрузка состояния при запуске происходит автоматически и бесшовно.
* Автоматически сохраняются выбранный репозиторий, папка назначения и состояние интерфейса, включая страницу, фильтры и сортировку. Сохранённая папка назначения используется как значение по умолчанию в системном диалоге выбора при следующем скачивании и не заменяет собой отображение этого диалога.
* Состояние не должно требовать отдельной кнопки Save.
* Каждая запись состояния выполняется атомарно.
* При повреждении или незавершённой записи должна сохраняться возможность восстановить последнее корректное состояние.

## 5. Ограничения GitHub API

* Реализация должна использовать актуальную документацию GitHub API как источник истины для доступных параметров, ограничений и поведения API.
* Список repository Issues поддерживает серверные параметры `state`, `labels`, `sort`, `direction`, `page` и `per_page`; текущий интерфейс должен ограничиваться возможностями API.
* GitHub API ограничивает `per_page` для этого endpoint значением 100; отображение по 10 карточек на странице является ограничением интерфейса приложения.
* GitHub API рассматривает pull requests как Issues в соответствующем endpoint, поэтому приложение обязано учитывать поле `pull_request` при формировании списка.
* Доступ к приватным Issues требует соответствующих прав токена; при недостаточных разрешениях приложение должно показать ошибку и предложить заменить токен.
* Реализация не должна добавлять локальную сортировку или фильтрацию там, где пользователь ожидает серверную сортировку/фильтрацию GitHub.
* Если требуемое пользователем поведение не поддерживается конкретным GitHub API endpoint, приложение должно либо использовать другой официальный endpoint, либо явно сообщить об ограничении, а не имитировать его незаметной полной локальной загрузкой.

## 6. Расширяемость

* Архитектура поведения должна оставлять возможность добавления дополнительных функций без изменения базового пользовательского сценария.

## 7. Общий пользовательский сценарий

* Пользователь запускает Upload My Issue.
* Приложение автоматически восстанавливает сохранённый репозиторий и состояние интерфейса.
* В верхней части отображаются авторизованный аккаунт и текущий репозиторий.
* При необходимости пользователь меняет репозиторий через URL или список доступных репозиториев.
* На Download пользователь видит существующие Issues выбранного репозитория с серверной фильтрацией, сортировкой и пагинацией.
* На Upload пользователь перетаскивает Markdown-файлы, вставляет их из Explorer или передаёт пути.
* Приложение рекурсивно обрабатывает папки, исключая symlink/junction.
* Файлы появляются во временной Upload-очереди.
* Для каждого файла автоматически определяется title.
* Пользователь при необходимости редактирует title, labels и другие доступные метаданные.
* Пользователь может фильтровать, сортировать, выделять и удалять карточки.
* Перед массовой отправкой выполняется локальная валидация.
* При более чем 10 Issues запрашивается подтверждение.
* Приложение отправляет Issues в GitHub.
* При ошибке пользователь принимает решение о продолжении или прерывании; при продолжении повторяются только неуспешные элементы.
* После завершения подтверждённой операции временная Upload-очередь очищается.
* На Download пользователь выбирает один или несколько Issues и запускает скачивание.
* Приложение сохраняет каждый Issue как `номер-title.md` в выбранную папку.
* Конфликты файлов никогда не разрешаются тихой перезаписью.
* Все долгоживущие операции можно отменить.
* Состояние приложения и настройки автоматически сохраняются в `AppData/upload-my-issue/`.
* Диагностические логи автоматически сохраняются в `AppData/upload-my-issue/logs`.
